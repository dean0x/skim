## ADR-001: Net-savings compression guard caps tokenization input and falls back to byte comparison on degenerate input

- **Date**: 2026-06-23
- **Status**: Accepted
- **Context**: the net-savings guard decides whether to compress by comparing token counts of raw vs compressed output, but BPE tokenization is O(n) per byte and degenerate low-entropy input (minified JS, base64) can drive worst-case cost up
- **Decision**: cap the guard tokenization input at TOKEN_SIZE_CAP=256 KiB (raised from 64 KiB) for more token-accurate compress/no-compress decisions, and add a separate TOKEN_RUN_CAP=4 KiB longest-nonwhitespace-run guard that, when exceeded, falls back to cheap byte-length comparison instead of tokenizing
- **Consequences**: 256 KiB covers virtually all real source files so analytics token counts stay faithful, while the run-cap byte fallback bounds the hot path against O(n^2)-style BPE blow-up on degenerate runs (the actual hazard, which scales with run length not file size, so a size cap alone does not protect it)
- **Source**: self-learning:obs_1782220902_5e702fe6

## ADR-002: Oversized-input COUNT caps degrade to a lossless --max-lines-honoring raw passthrough instead of hard-erroring 'Too many ... Possible malicious input'. DEPTH caps and the 50MB MAX_INPUT_SIZE stay HARD errors. The degrade is fail-loud: a SKIM_DEBUG notice plus an output tier labeled 'degraded' (never silently 'full'). Rationale: count caps never bounded parse cost (parse is bounded by MAX_INPUT_SIZE, checked BEFORE any count cap), so a fail-open degrade weakens no DoS defense while honoring the #317 compress-never-truncate MUST.

## ADR-004: skim's agent-hook install pins the hook script to the ABSOLUTE, shell-quoted path of the installing binary plus that build's commit sha (SKIM_HOOK_BINARY/SKIM_HOOK_COMMIT); build.rs embeds the short sha into --version (2.10.0 (<sha>)); the currency predicates are INVERTED so `skim init` re-run UPGRADES a stale script instead of skipping it; check_hook_binary_mismatch detects installed-hook-vs-running-binary drift. Rationale: a bare `skim` on $PATH can resolve to a DIFFERENT/stale clone on a divergent branch (a documented recurring hazard), silently exercising the wrong binary; pinning the absolute binary+sha and self-healing stale scripts on re-init guarantees the hook always drives the exact binary that installed it, with a build-identity handshake so drift is observable.

- **Date**: 2026-07-05
- **Status**: Accepted
- **Context**: skim installs itself as an agent PreToolUse hook (Claude/Cursor/Codex/Gemini/Copilot/Crush via `skim init`). The hook previously invoked skim in a way that could resolve to whatever `skim` was first on $PATH -- which on this machine can be a DIFFERENT/stale clone on a divergent branch (documented recurring hazard in CLAUDE.md 'Commands' and MEMORY.md skim-bash-path-resolves-wrong-clone), silently exercising the wrong binary
- **Decision**: pin the hook script to the ABSOLUTE, shell-quoted path of the installing binary plus that build's commit sha (SKIM_HOOK_BINARY/SKIM_HOOK_COMMIT)
- **Consequences**: guarantees the hook always drives the exact binary that installed it (defeats wrong-clone / stale-PATH resolution, the #1 operational footgun in this repo), makes staleness detectable and self-healing on re-init, and gives a build-identity handshake (sha in --version) so drift is observable. Trade-off: hook scripts become machine/build-specific (absolute path + sha) rather than portable, so they must be re-generated per install rather than checked in. Shipped in PR #421 (F6, commit a9aa3e1)
- **Source**: self-learning:obs_1783253010_hookpin

## ADR-005: skim's agent-facing guidance template (guidance_content() in cmd/init/helpers.rs, installed by `skim init` between <!-- skim-start v{ver} --> markers into every agent's instruction file) is deliberately framed as SCOPE + calibrated-trust ('treat skim as a lens, not a source'), NOT as a list of output-CORRECTNESS guarantees. Rationale: any 'skim guarantees X' clause becomes a false promise the day a bug ships in path X, and worse, an agent told 'skim guarantees X' rationalizes away real evidence of X breaking -- so guidance asserts only the INTENDED SCOPE (which tools get wrapped, e.g. bare `ls`/`grep`/`git diff` -> `skim <tool>` is intended, not a bug), which no future bug can falsify, plus where ground truth lives (raw output is authoritative). Corollary (reaffirmed this session, protected by a NEGATIVE test assert !content.contains("SKIM_PASSTHROUGH")): the guidance deliberately does NOT name SKIM_PASSTHROUGH=1 as a verify-with-raw escape hatch -- empirically, agents that learn it use it by default and bypass compression entirely instead of letting skim work; they learn it from stderr hints instead.

- **Date**: 2026-07-08
- **Status**: Accepted
- **Context**: skim installs a guidance block into agent instruction files via `skim init` (guidance_content() in crates/rskim/src/cmd/init/helpers.rs, marker-wrapped for idempotent re-init). The existing template over-weights the file-reading surface and under-explains command-wrapping, which caused agents to misreport intended behavior (bare `ls`/`grep` rewritten to `skim <tool>`, the `[skim] ... exited N
- **Decision**: frame that guidance as (1) a SCOPE statement -- which tools get wrapped and that wrapping is intended, not a bug -- and (2) a calibrated TRUST hierarchy -- 'treat skim as a lens, not a source
- **Consequences**: (a) any guarantee ('never net-larger', 'operators preserved byte-for-byte') becomes a false promise the moment a bug ships in that path, and an agent primed with 'skim guarantees X' will rationalize away real evidence of X breaking -- so guidance must claim only what a future bug cannot falsify (SCOPE: which tools are wrapped) and where ground truth lives (raw output), never output correctness
- **Source**: self-learning:obs_1783523562_guidframe

## ADR-006: skim hook responses NEVER self-approve: skim emits a permission allow verb ONLY where the host protocol strictly requires a decision field (Cursor permission:allow; Gemini/Crush decision:allow) and otherwise returns a verb-free transform (Claude updatedInput; Copilot modifiedArgs-only, no permissionDecision; Codex install-time rules only), always deferring the real grant to the host allowlist or human operator. Permissions seeding (skim init --permissions) is a SEPARATE install-time, human-consent-gated channel: a TTY-gated prompt is required before any entries are written and --yes never bypasses it, so a non-TTY agent (whose Bash tool is never a TTY) can never self-grant.

- **Date**: 2026-07-11
- **Status**: Accepted
- **Context**: skim is a PreToolUse hook across six agent runtimes (Claude Code, Cursor IDE, Gemini, Crush, Copilot CLI, Codex) whose hook-response schemas differ in whether a permission verb is required, and v2.11.0 adds install-time allowlist seeding via skim init --permissions, creating a recurring risk that skim self-approves tool calls (emitting an allow verb where the protocol does not require one, bypassing the agent own allow/deny policy) or conflates seeding allowlist entries with granting runtime approval
- **Decision**: skim NEVER self-approves -- it emits a permission allow verb ONLY where the host protocol strictly requires a decision field and otherwise returns a verb-free transform, always deferring the real grant to the host allowlist or human operator, and it makes permissions seeding a SEPARATE install-time human-consent-gated channel with a TTY-gated prompt required before any entries are written, --yes never bypassing it, and Codex opt-in-only with the blanket tier refused
- **Consequences**: skim can never be used as a policy bypass because it only passes transformed input through the host normal approval flow or, at install time, seeds entries a human explicitly consented to via TTY prompt
- **Source**: self-learning:obs_1783804633_noselfapprove

## ADR-007: skim pseudo mode should PRESERVE function return types (Rust/Python/TypeScript), NOT strip them: return types are API surface, not syntactic noise, extending the A4 'API surface is not noise' contract that commit c244a12/#367 established when it stopped stripping visibility modifiers on the same rationale. The reported 'structure mode drops -> bool' bug is a misdiagnosis: direct skim file.rs (structure/signatures/minimal) preserves return types; the loss happens only because the cat/head/tail rewrite (mode_for_files, handlers.rs:44-52) selects --mode=pseudo for regular code files and pseudo deliberately strips return types (strip_rust_return_type pseudo.rs:597; Python/TS return_type/type_annotation in strip_kinds). Design fork resolved by the user: fix pseudo to keep return types (Fork A) rather than switch cat->structure (Fork B), because structure drops function BODIES and cat-readers want the logic. Scope Rust+Python+TypeScript -- the only three langs that strip return types in pseudo (Go/Java/C/C++/C#/Kotlin/Swift already preserve them), so this is an inconsistency, not an invariant.

- **Date**: 2026-07-13
- **Status**: Accepted
- **Context**: a coding-agent bug report claimed skim 'structure mode' drops function return types (-> bool). Validation (skim 2.11.0/6099453) showed structure/signatures/minimal preserve return types
- **Decision**: preserve return types in pseudo mode for Rust, Python, and TypeScript -- treat return types as API surface (Fork A), NOT change cat's mode selection to structure (Fork B). rationale: (1) structure mode drops function BODIES
- **Consequences**: (1) structure mode drops function BODIES

## ADR-011: skim's stderr notices are split into TWO classes with opposite visibility defaults: (1) ELISION / transparency markers -- emitted when the reader is actually shown LESS than (or something different from) the raw tool -- stay UNCONDITIONAL and must carry exact counts plus the SKIM_PASSTHROUGH=1 hint; (2) RAW-FALLBACK BANNERS -- emitted when skim chose to show the raw bytes, i.e. NO data was lost -- are gated behind SKIM_DEBUG/--debug (crate::debug_log! / io::sink()) so they cost ZERO bytes by default. Rationale: agent harnesses capture stderr, so a no-loss banner is pure context tax with no actionable content, while a loss-bearing marker is the only signal that raw differs from what was shown and must never be silenceable. Constraint on future work: every new stderr notice must be classified before it is added -- if it can fire when the reader sees less/different, it is a marker (always on); if it fires only on a lossless raw fallback, it is a banner (debug-gated). Do NOT re-conflate the two.

- **Date**: 2026-07-25
- **Status**: Accepted
- **Context**: skim emits several stderr notices from its wrapper paths. Two of them are semantically opposite but had been drifting together in contributors' minds: an ELISION marker means the reader was actually shown LESS than raw (a real truncation/omission, #317-relevant), whereas a RAW-FALLBACK BANNER means skim declined to compress and printed the raw bytes -- i.e. nothing was lost and the reader needs no action. Because agent harnesses capture stderr into the model's context, every unconditional banner is a per-invocation context tax, and five such no-loss banners were firing unconditionally (guardrail chose raw, wrapped tool exited unexpectedly, wrapped tool killed, multi-file guardrail trigger count, git show raw fallback). decision: gate the no-loss RAW-FALLBACK banners behind SKIM_DEBUG/--debug (via crate::debug_log! or routing the writer to io::sink() when !is_debug_enabled()), and keep every LOSS-BEARING marker unconditional -- elision markers (exact counts + SKIM_PASSTHROUGH=1 hint) and the ADR-008 lossy-view transparency marker are explicitly untouched. rationale: the two notice classes carry inverted value -- a no-loss banner has no actionable content for the reader and only burns context (and, per ADR-005's misreport pattern, invites false bug reports about skim 'doing something'), while a loss-bearing marker is the ONLY signal that what was shown differs from raw and is therefore load-bearing for the #317 compress-never-truncate MUST
- **Decision**: gate the no-loss RAW-FALLBACK banners behind SKIM_DEBUG/--debug (via crate::debug_log! or routing the writer to io::sink() when !is_debug_enabled()), and keep every LOSS-BEARING marker unconditional -- elision markers (exact counts + SKIM_PASSTHROUGH=1 hint) and the ADR-008 lossy-view transparency marker are explicitly untouched. rationale: the two notice classes carry inverted value -- a no-loss banner has no actionable content for the reader and only burns context (and, per ADR-005's misreport pattern, invites false bug reports about skim 'doing something'), while a loss-bearing marker is the ONLY signal that what was shown differs from raw and is therefore load-bearing for the #317 compress-never-truncate MUST

## ADR-012: skim NEVER filters terminal escape sequences that originate in wrapped-file CONTENT, but DOES neutralize a wrapped tool's OWN colorization at the child-invocation boundary (`--no-color`): content bytes reach the reader byte-faithfully on BOTH passthrough and skim-SYNTHESIZED renders (e.g. the patch-content lines cmd/file/diff.rs emits, which are skim's own construction rather than a copy of the tool's output), while the tool's colorization never enters the pipeline in the first place (git/diff/mod.rs:281-283, git/show.rs:426-428 and :741-744 -- the latter documents it as a defense against user configs setting `color.ui = always`, i.e. TOOL colorization, MEDIUM-17). `skip_ansi_strip: true` on diff (cmd/file/diff.rs:39), grep (cmd/file/grep.rs:29) and rg (cmd/file/rg.rs:27) is the mechanism that makes the content half true. The terminal-escape-injection exposure is accepted as inherent to a cat/grep-class reader and is the CALLER's (terminal / agent harness's) problem, not skim's. Scope: cmd/file/diff.rs, cmd/file/grep.rs, cmd/file/rg.rs, cmd/git/diff/render.rs, cmd/git/show.rs. Consequence, stated explicitly: a human viewing skim output on a TTY can see content-controlled escape sequences exactly as they would running the raw tool, and agents reading piped output receive the raw bytes. Corollary rule for future work: per-field `strip_ansi` on already-SPLIT METADATA fields (paths at cmd/file/diff.rs:303 and :313, check names at cmd/infra/gh/pr_checks.rs:190 and :211) remains correct and is NOT what this ADR prohibits -- the prohibition is on filtering CONTENT. Constraint on future work: do not add an escape/control-byte filter to any wrapper or synthesized render, and do not treat "skim renders it, so skim owns sanitizing it" as a reason to diverge -- synthesized renders follow the same raw-content rule as passthrough. Supersedes nothing; resolves the ESCALATED review finding security-02 as BY_DESIGN.

- **Date**: 2026-07-25
- **Status**: Accepted
- **Context**: PR #456 Fix 2 made `skim diff a b` emit actual patch BODY lines (previously only `path: +N, -M` stat lines, cmd/file/diff.rs), and those body lines are file CONTENT that may carry ESC/CSI/OSC bytes. A security review (finding security-02 in .devflow/docs/reviews/fix-agent-reported-batch-2/2026-07-25_1722/security.md) ESCALATED this for a human ruling rather than dispositioning it, because the proposed remedy collides head-on with the sibling decision on grep/rg (architecture-01 / regression-01 / rust-06), which asked skim to STOP stripping for PF-006 tab-preservation reasons -- the triager noted the two are one decision viewed from opposite ends and must be resolved together. Two mutually exclusive directions were on the table: (a) accept raw content bytes everywhere, (b) add a tab-preserving escape-only filter for synthesized renders
- **Decision**: (a) -- accept raw. skim does NOT filter escape or control bytes sourced from file CONTENT, in passthrough OR in skim-synthesized renders, and DOES neutralize the wrapped tool's OWN colorization by passing `--no-color` to the child invocation. Content-derived bytes are never stripped, tool-emitted colorization never gets generated. Scope: cmd/file/diff.rs, cmd/file/grep.rs, cmd/file/rg.rs, cmd/git/diff/render.rs, cmd/git/show.rs
- **Consequences**: (1) native `diff` / `grep` emit the same content bytes, so skim sitting in the pipeline adds ZERO exposure delta. (2) Filtering means showing LESS than the raw tool, which violates the #317 compress-never-truncate MUST in CLAUDE.md -- the reader would see something DIFFERENT from raw with no marker. (3) No tab-preserving escape filter exists in the codebase: the ONLY sanitizer, `sanitize_for_display` (crates/rskim/src/cmd/security.rs:356), is ASCII-graphic-only plus a 64-char truncation, so it destroys tabs (PF-006) and all non-ASCII, and it is scoped to unknown-tool ERROR messages, never to content. Adopting `strip_ansi_escapes::strip_str` for content would re-introduce the already-fixed PF-006 data loss, and a bespoke tab-preserving filter is new hand-rolled parsing on the hot path of every wrapper. (4) Universal existing precedent: every wrapper that emits content into a synthesized render already passes those bytes through unmodified -- `crates/rskim/src/cmd/git/diff/render.rs` (emit_patch_line at :854, closing-brace source-line emission at :610, and the Full-mode source-line emission in render_unchanged_node from :622) and `crates/rskim/src/cmd/git/show.rs` (run_show_file_content at :720). (5) The consistent and only ANSI defense across skim is `--no-color` on the CHILD invocation (git/diff/mod.rs:281-283, git/show.rs:426-428 and :741-744, the latter explicitly documented as a defense against user configs setting `color.ui = always`, i.e. TOOL colorization, MEDIUM-17) -- a boundary-level neutralization that costs no fidelity because it prevents bytes from ever being generated rather than removing bytes after the fact. (6) An escape that survives is visible and caller-controllable, whereas a stripped tab is silent -- prefer the failure mode the reader can see. Consequence, stated explicitly: a human viewing skim output on a TTY can see content-controlled escape sequences exactly as they would running the raw tool, and agents reading piped output receive the raw bytes. Corollary: per-field `strip_ansi` on already-SPLIT METADATA fields (paths at cmd/file/diff.rs:303 and :313, check names at cmd/infra/gh/pr_checks.rs:190 and :211) remains correct and is NOT prohibited by this ADR -- the prohibition is on filtering CONTENT. This ADR supersedes nothing and resolves the ESCALATED security-02 as BY_DESIGN, with `skip_ansi_strip: true` on diff (cmd/file/diff.rs:39), grep (cmd/file/grep.rs:29) and rg (cmd/file/rg.rs:27) as the mechanism that makes it true. Constraint on future work: any proposal to sanitize output must first show it loses no bytes and does not regress PF-006, and must not treat a synthesized render as a reason to diverge from the raw-content rule
- **Source**: self-learning:obs_1785012120_contentescape

## ADR-014: Passthrough wrappers must set skip_ansi_strip: true — the strip runs upstream of parse() and shadows `output`; RawPassthrough does NOT bypass it

- **Date**: 2026-08-07
- **Status**: Accepted
- **Context**: PR #456 converted six file wrappers (wc, df, du, find, ps, ls) to byte-faithful passthrough via `ParseResult::RawPassthrough`, but all six were left at `skip_ansi_strip: false`. In `execution.rs` the ANSI-strip step runs BEFORE `parse()` and shadows the `output` binding — so a `parse_impl` that returns `RawPassthrough` serves the ALREADY-STRIPPED bytes, not the raw bytes. `strip_ansi_cow` is all-or-nothing across the whole buffer: one ESC byte anywhere causes `Cow::Owned`, and `strip_ansi_escapes` drops ALL C0 controls (including `\t` 0x09) from the entire buffer. One colorized filename in `du` output therefore destroyed the POSIX tab separator on every line. Measured at HEAD: `CLICOLOR_FORCE=1 ls -G` produced 0 ESC bytes vs 9 from raw; `du -a` on a dir with a literal ESC byte in one filename produced 0 tabs on ALL three lines and corrupted the ESC-bearing filename from `esc\x1bname` to `escame` (ESC + following byte consumed as a 2-byte sequence).
- **Decision**: flip `skip_ansi_strip` from `false` to `true` in wc.rs, df.rs, du.rs, find.rs, ps.rs, and `CONFIG_LS` in ls.rs. The correct trigger condition is NOT "wrappers that parse tabs" but "any wrapper whose bytes reach the reader unparsed (RawPassthrough) MUST set `skip_ansi_strip: true`"; converting a wrapper to passthrough IS the moment the flag must flip. This completes ADR-012's scope — which made the content-bytes half true for diff/grep/rg via their `skip_ansi_strip: true` flags — across the passthrough family. `CONFIG_TREE` in ls.rs stays `false` deliberately because tree genuinely parses its output via `RE_TREE_ENTRY` (box-drawing regex); ANSI stripping before the regex runs is correct for tree. A unit test in ls.rs pins `CONFIG_TREE.skip_ansi_strip == false` to make the asymmetry with `CONFIG_LS` visible. `env.rs` stays `false` because env parses and redacts (not passthrough). The comment in `execution.rs` is rewritten to state (a) the ordering — strip happens before `parse()`; (b) it shadows the `output` binding; (c) `RawPassthrough` does NOT bypass the strip; (d) the flag must be `true` for any wrapper whose bytes reach the reader unparsed.
- **Consequences**: wc/df/du/find/ps/ls now emit byte-identical output including TAB (POSIX column separators) and ESC (tool colorization, file-content bytes) to the reader, closing the filename-corruption regression. ADR-012's decision that skim never strips content-borne escape sequences is now true on ALL three wrapper families (tab-parsing, passthrough). Rejected alternative: "skip the strip when the result is `RawPassthrough`" — rejected because it requires an owned unstripped `CommandOutput` alongside the stripped one on every wrapper invocation (allocates against the 64 MiB ceiling on the hot path, violating the hot-path allocation constraint); it would silently change behavior for every `skip_ansi_strip: false` tool on a raw-emission path, including the whole infra family; and it covers only one of three raw-emission paths while looking complete.
- **Source**: fix/agent-reported-batch-2 commit (ADR-014)
